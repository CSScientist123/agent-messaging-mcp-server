# Messaging MCP: architecture and rationale

**Audience.** An engineer who will maintain and debug this system without its author present — someone who needs to understand not just what each piece does but why it is shaped the way it is, so that a future change can be judged against the same reasoning rather than against guesswork.

**Scope.** The system's purpose; the relationship between `MessagingCore` (`messaging_core/core.py`), the schema it sits on (`schema/schema.sql`), the three MCP server processes that embed it (`mcp_server/server.py`, `mcp_server/config.py`), the extension boundary (`extension/base.py`, `adapters/registry.py`), and the Polling Server (`polling/server.py`); the identity and addressing model; the roles that chain the three remotes together; and the concurrency guarantees the whole thing rests on.

**Non-scope.** Parameter-by-parameter behavior of the eighteen capabilities, the rejection-code index, and the schema's column-level reference — all of that is `docs/02-reference.md`, and this document links to it rather than repeating it. The step-by-step mechanics of a message's life from admission to delivery are `docs/03-message-lifecycle.md`. How to run, configure, or troubleshoot a live deployment is `docs/04-operating-and-debugging.md`.

**Assumed prior knowledge.** Python, SQLite (transactions, `PRAGMA`, foreign keys, triggers), and roughly what MCP (Model Context Protocol) is — a way to expose callable tools to an agent over some transport.

---

## What the system is for

The premise is narrow and worth stating plainly: agents delegate work to other agents, those other agents live inside three different remote applications, and no agent ever polls for a result. An agent that hands off a piece of work — "look into this," "answer this question," "keep going, but now with this changed permission" — needs to move on immediately rather than sit in a loop asking "are you done yet?" Somewhere, something has to do the waiting on its behalf, notice when the far side gets stuck, and hand the outcome back only once there is one. That somewhere is this system: a small, shared bookkeeping layer (`MessagingCore`) that every participant's requests pass through, and a background component (the Polling Server) that does all the actual watching so that no agent has to.

Three remote applications sit behind this: NotebookLM, a source of context that answers questions about material loaded into it but never acts on its own; Claude Science, which runs frames of agentic work against a local HTTP API; and Antigravity, which runs conversations inside `tmux` sessions driven by the `agy` CLI. An agent that wants something from one of these doesn't reach out to it directly — it registers itself and its target as **Partners** in a shared database, establishes a **Handshake** where one is required, and then calls **`send`**. What happens after that point is this system's job, not the calling agent's.

## The Messaging Server is a logic class, not a server

The name is worth pausing on, because it is easy to misread. `MessagingCore` has no transport, no port, no listening socket, and no process of its own — it is an ordinary Python class with a database handle and, optionally, one `RemoteExtension`. Three separate MCP server processes each construct their own `MessagingCore` instance, paired with the Polling Server that watches for its results (`mcp_server/config.py: build_stack_from_env`), one per remote-executing source, and each exposes that instance's eighteen capabilities as MCP tools (`mcp_server/server.py: build_server`). There is no fourth process coordinating between them, and no RPC call from one `MessagingCore` to another.

What makes the three instances behave as one shared system is not a network protocol between them — it is that they all point at the same SQLite file, governed by the same schema (`schema/schema.sql`). When a Claude Science partner calls `handshake` against an Antigravity partner, the row that authorizes it lands in the one `handshakes` table that both of those processes' cores read from. When one process's core admits a message into `message_queue`, that row is visible, immediately, to whichever process's Polling Server drain thread is watching the target Partner — because it is watching the same table, not because anyone told it to. The database *is* the integration layer.

This is a deliberate choice, not an oversight. A transport between the three cores — an internal RPC layer, a message bus, a socket the cores speak to each other over — would buy this system nothing it doesn't already have through the shared schema, and it would add a failure mode that doesn't otherwise exist: a place where two cores can disagree about state, or where one can be unreachable while the other is fine. SQLite's own transactional guarantees (see below) already give every core a single, consistent view of the world; layering a second consistency mechanism on top of that would be solving a problem the schema doesn't have.

## The extension layer

Eighteen capabilities live on `MessagingCore`. Eleven of them — `search_partner`, `search_project`, `delete_partner`, `delete_project`, `claim_orchestrator`, `grant_gemini_budget`, `archive_sessions`, `status`, `handshake`, `read`, and `extend_project` — finish entirely from local state: a `SELECT`, a business-rule check, a write, and a return value, with nothing that has to leave the process. The other seven — `create_project`, `create_partner`, `send`, `interrupt_partner`, `get_permissions`, `add_permissions`, and `delete_permissions` — cannot finish without reaching out to whichever remote application the target Partner's Project belongs to.

Underneath those seven sit only four abstract methods on `RemoteExtension`: `verify_project_system_id`, `verify_partner_id_in_remote`, `deliver_message`, and `stop_remote_execution`. There is deliberately no fifth for resuming. Correcting whatever blocked a Partner and sending the work again *is* the resumption, so a remote-side resume would be a second way to start work — one that skips the queue, which is where priority is decided.

The line between local and remote is worth stating as a principle, because "involves a remote" is not it. `handshake` can connect two Partners that belong to entirely different remote applications — a `science_` Partner to a `gemini_` Partner is the sanctioned cross-source pairing — and yet `handshake` never touches an extension at all; every fact it needs (the two Partners' types, roles, project memberships, existing handshake rows, budget) already lives in the local schema. The real boundary is narrower and more useful: **an extension is needed exactly where the data or the effect the capability needs actually lives on the remote side**, not merely because a remote application is involved in the story. `create_project` and `create_partner` need an extension because the thing being verified — does this project, does this session, really exist over there — is a fact only the remote can answer. `send` and `interrupt_partner` need one because both end up in `advance`, and advancing the queue means literally handing a prompt to a Partner's remote counterpart (and, when a task is displaced, stopping that counterpart first). The three permission capabilities need one because a read/write grant is held by the remote, not by this database — `partner_paths` records what the grant is *meant* to be, and only the remote knows what it actually is.

`read`, by contrast, is local for every source, including the two that execute. The reason is not that `read` is special-cased by source — `MessagingCore.read` is one query, unconditionally, against the local `messages` table, for every Partner regardless of what kind it is. The reason `read` never needs to reach out is that, for Claude Science and Antigravity, whatever ends up worth reading already arrived in the shared database through entirely local means: the executing Partner is itself an agent, so when it has something to report it calls `send` — the same capability everything else uses — and that message is admitted locally, in the same way any other message is, before delivery is even attempted. NotebookLM is the one genuine exception, and it is an exception at the extension boundary, not inside `read` itself: NotebookLM cannot act on its own — it has no `send` tool of its own to call back with — so nothing it produces would ever land in the shared database unless something reached in and pulled it out. That is exactly what `NotebookLMExtension.read_remote_result` exists to do, and it is the only one of the three real adapters that implements this for real; `ClaudeScienceExtension` and `AntigravityExtension` both inherit the base class's default, which raises `NeedsRemote`, because their Partners are expected to report results by acting, not by being read from. When the Polling Server hits that `NeedsRemote` for those two sources, it falls back to a placeholder string rather than treating it as a failure (`PollingServer._read_result`) — the real content, for those two, was never expected to come from that call in the first place.

## The three adapters

Each adapter subclasses `extension.base.RemoteExtension` (or, for a remote that never executes, `NonExecutingExtension`) and fixes one `source_prefix`. Underneath the shared vocabulary of Project, Partner, and Message, each adapter maps those three concepts onto a genuinely different shape of remote:

| Adapter | `source_prefix` | Project maps to | Partner maps to | Message maps to |
|---|---|---|---|---|
| `NotebookLMExtension` | `nlm_` | a NotebookLM notebook | a source inside that notebook | a `notebook query` and its answer |
| `ClaudeScienceExtension` | `science_` | a Claude Science project | a frame within that project | a turn submitted to that frame |
| `AntigravityExtension` | `gemini_` | a filesystem folder | a conversation (a `tmux` session) | a typed turn sent into that session |

NotebookLM's mapping carries three consequences worth naming explicitly, and all three are rows in `source_caps` rather than branches in code.

**A source never executes** (`can_execute = 0`). That is why `NotebookLMExtension` subclasses `NonExecutingExtension`, which supplies `stop_remote_execution` as an unconditional `Rejected("not_executable", ...)` refusal rather than leaving it abstract — there is nothing to stop for a Partner whose Project cannot execute, and `_require_executable` (`core.py`) is the one check that turns that into a clean, documented refusal rather than a confusing failure three layers down.

**A source never sends** (`can_send = 0`). There is no agent behind a notebook; nothing there ever decides to speak. A NotebookLM Partner is reachable but is never a Caller, and `send` refuses with `source_cannot_send` if one tries.

**A source never takes delegated work** (`accepts_research = 0`). `[RESEARCH]` asks its recipient to go and do something, and NotebookLM only answers questions about material it already holds. A `[RESEARCH]` aimed at one is refused with `research_not_accepted`.

Claude Science and Antigravity, by contrast, genuinely execute — a frame or a conversation is a running process with its own turn-taking — which is why their extensions implement `stop_remote_execution` for real and why `interrupt_partner` is a meaningful capability against them at all. Of the three, only Antigravity implements the permission trio: a Claude Science frame has no per-frame path concept for a grant to attach to, so its adapter inherits the base class's refusal rather than pretending otherwise.

## Identity and addressing

Two facts anchor everything else in this system, and they are worth holding side by side because the second follows from the first.

The first is that **a Partner has no source of its own**. `projects.source_prefix` is the single authority for what kind of remote a family of Partners belongs to, and a Project has exactly one `source_prefix` — enforced structurally, since it is a single column on a single row. A Partner simply inherits its Project's value (`MessagingCore._partner_type` is nothing more than a join from `partners` to `projects`). Two Partners registered under the same Project therefore always share a type; there is no way, short of registering a second Project, for two differently-sourced Partners to appear as if they belonged together.

The second is that titles and UUIDs answer two different questions. A **title** is a free-form, server-wide-unique, human-readable address — the string one agent uses to name another when calling `handshake` or `send`. A title is resolved to a row **immediately, at the boundary**, the moment a capability looks it up (`_resolve_live_partner_by_title`), and it carries no type information at all — nothing about a title tells you whether it names a `science_` Partner or a `gemini_` one. A **UUID**, by contrast, is the only identity credential a Partner ever holds; it is minted once, at `create_partner`, shown exactly that one time, and used as `requester_uuid` for every subsequent call that Partner ever makes. Everywhere inside the system — every join, every check, every foreign key — identity travels as an internal row ID or a UUID, never as a title. Titles exist for humans and agents to type; internal plumbing never touches them except to translate one into the other.

Put those two facts together and a consequence falls out that could otherwise look like an inconsistency: **a cross-source handshake is cross-Project by construction.** Because a Project has exactly one `source_prefix`, any two Partners that share a source necessarily share the possibility of sharing a Project, and any two Partners with *different* sources necessarily belong to different Projects — there is no other way for the numbers to come out. This is why `MessagingCore.handshake`'s "both partners must belong to the same project" rule (the `different_project` rejection) is written to apply only when the two Partners' types are equal: applying it universally would make the one sanctioned cross-source pairing — a `science_` Partner reaching a `gemini_` Partner, the bridge that lets Claude Science hand work to Antigravity at all — impossible to ever satisfy. The rule isn't an exception carved out for this one case; it is scoped correctly from the start once you see that "same source" and "same Project" are the only combination the rule was ever meant to police.

## The manager/worker chains

Two management relationships run through this system, and they use the mechanisms above in different ways.

Claude Code manages Claude Science, and it does so through exactly one door. A `code_` Partner may handshake precisely one counterpart: a `science_` Partner holding the `bridge-scientist` role — and that bridge may hold at most one `code_` Partner in return (`code_handshakes_bridge_only`, `bridge_single_code_partner`). That pairing is the entire reason the `bridge-scientist` role exists. It is the seam between a human's Claude Code session and the research project, and a seam with two ends on one side is not a seam: a bridge holding two `code_` Partners would make "the Caller" ambiguous for every message that reached it.

Two details about that rule are easy to miss and both are deliberate.

First, a `code_` requester is **exempt from the "only an orchestrator may initiate a handshake" rule**. It has to be: the three `orchestrator_type` values are all Claude Science roles, and none of them fits a local Claude Code session, so a `code_` Partner can never hold one. `handshake` therefore checks the `code_` case first and separately, before the orchestrator check it could not pass.

Second, the bridge's *other* legal counterpart is the `project-orchestrator`, and nothing else in the project (`bridge_handshakes_orchestrator_or_code`). The bridge takes direction from Claude Code and passes it to the orchestrator; it has no business wiring up anything else. That is also why it sits at layer 1 in `agent_layers`, between Claude Code at 0 and the project-orchestrator at 2.

`adapters/registry.py` reinforces the boundary one level down: `build_extension("code_")` raises `Rejected("no_adapter_for_code", ...)` outright, because Claude Code, running locally, has no remote presence of its own for a `RemoteExtension` to reach. NotebookLM, `gemini_`, and `science_` each have a real application on the other end of their prefix; `code_` does not.

Claude Science manages Antigravity, and it does so through a role, not through the schema's Partner type. `gemini-orchestrator` is one of the three fixed `orchestrator_type` values a Partner may claim (alongside `project-orchestrator` and `bridge-scientist`). **All three are Claude Science roles** and can only ever be claimed inside a `science_` Project — `claim_orchestrator` checks the *claiming Partner's own Project's* `source_prefix`, not anything about the target, and rejects with `orchestrator_requires_science_project` otherwise. An earlier version restricted only `gemini-orchestrator`, which left an Antigravity or NotebookLM Partner free to claim the other two; nothing crossed a boundary because every path was independently guarded, but "currently unreachable" is not a rule. The name is easy to misread as "an Antigravity partner that orchestrates gemini work," but it names the opposite: it is a **Claude Science** agent that holds the authority to reach into Antigravity — to handshake toward a `gemini_` Partner (`requires_gemini_orchestrator`), spend a granted budget of such handshakes (`grant_gemini_budget`, `no_gemini_budget`, `gemini_budget_exceeded`), and thereby become the one Claude Science session a given Antigravity conversation is allowed to take direction from (`gemini_single_science_source` refuses a second, different `science_` sender from ever handshaking the same `gemini_` target). This is the concrete mechanism behind "Claude Science manages Antigravity": not a special relationship encoded anywhere as such, but the ordinary handshake rules, applied to a role that only a `science_` Partner is permitted to hold.

## Where the concurrency guarantees come from

Every write in this system goes through exactly one path: `Database.write(fn)`, which hands `fn` to a single, dedicated writer thread and blocks the caller until it returns. That thread, and only that thread, ever opens `BEGIN IMMEDIATE` — SQLite's mode for acquiring the write lock up front, before any statement inside the transaction runs, rather than discovering a conflict partway through — and commits or rolls back as one unit (`Database._run_write`). Nothing else in the codebase issues a write outside this path; the per-`(caller, label)` cap, the live-partner limit, the orchestrator-role uniqueness, all of it is enforced by SQL running under this one thread's transactions.

One piece of state is deliberately outside all of this, and it is worth saying why. The **working slot** — the single task a Partner is actually being worked on — lives in process memory (`messaging_core/slots.py`), never in SQLite. It is process state: it changes on every swap, it is meaningless to a second process (only the Polling Server that owns the drain thread can act on it), and it does not survive a restart because the remote's own turn does not survive one either. Persisting it would put a row in the database that a reader would reasonably take for durable truth, and that reader would be wrong in exactly the situation where being wrong is expensive — after a crash, when the row says a Partner is mid-task and no thread is driving it. Its locking is per Partner rather than global, because a swap holds its lock across a remote round trip; under one lock every drain thread would queue behind whichever Partner's remote was slowest, which is the opposite of why the drain threads exist.

Reads take a different, and equally deliberate, route. Every reading thread gets its own connection, and for the on-disk case that connection is opened against a `file:...?mode=ro` URI (`Database._new_reader_connection`) rather than a plain path. This detail matters more than it looks: `mode=ro` denies write access at the level of the operating system's file descriptor, before SQLite's own logic ever gets a say. Contrast that with `PRAGMA query_only = ON`, which the same reader connection also sets, as defense in depth — a pragma is just another statement, and any caller who can pass SQL to `read()` can pass `PRAGMA query_only = OFF` right back. The test suite proves this distinction is not academic: `tests/test_boundaries.py::test_read_query_only_pragma_permanently_disables_read_only_enforcement` deliberately flips that exact pragma off through the public `read()` method, on a real on-disk database, and confirms that the very next `INSERT` attempted through `read()` still fails — because the file descriptor underneath the connection was never given write access in the first place, and no SQL statement can hand it what the operating system refused to. That is the whole argument for why read-only has to be a property of the connection rather than a togglable setting on it: a setting can be switched off by the very API it exists to guard; a permission the OS never granted cannot be argued back into existence by any statement running inside that connection.

The one deliberate exception is `:memory:`, used mainly for tests: an in-memory SQLite database exists only inside the single connection that created it, so there is no second file descriptor to open read-only against. `Database` routes both reads and writes through the one writer thread's shared connection in that case, toggling `PRAGMA query_only` around each read job — the pragma-based guard is what's available when there is only one connection to have, and the module docstring is explicit that `:memory:` is "the one exception" to the on-disk model rather than a second, equally-trusted mode.

## What the design rules out, and what it costs

A single `MessagingCore` holds at most one `RemoteExtension` at a time. This is stated plainly in the class's own docstring, and it is not a limitation that slipped in by accident — it is the direct consequence of the extension boundary described above: an extension's whole job is to speak for one family of remote, verified against one `source_prefix`, and a core that tried to hold several would need some other rule for choosing which one applies to a given Partner, a rule the schema's single-`source_prefix`-per-Project design already makes unnecessary. `_extension_for` treats a configured extension for the *wrong* source exactly as it treats no extension at all — both raise `NeedsRemote` — precisely so that a capability never ends up asking the wrong remote a question and fabricating an answer from whatever it got back.

The cost of that choice is direct: **one core speaks one source**, so any flow that crosses sources needs two cores, each embedded in its own MCP server process, talking to the same database rather than to each other. The `science_ → gemini_` handshake is the clearest example already discussed above, but the same shape recurs anywhere a Claude Science Partner needs to reach an Antigravity one, or anywhere a `code_` Partner reaches its `bridge-scientist`: the admitting core and the delivering core are never the same process, and the *only* thing that lets the second one pick up where the first left off is that both are reading and writing the one shared schema. There is no cross-core call, no internal handoff message, and no shared Python state between them — which is exactly the same trade this document opened with. A transport between the cores would make this flow feel more like "one system," but it would also introduce exactly the kind of failure mode — partial delivery, disagreement about state, a call that succeeds on one side and is never known about on the other — that routing everything through one transactional database was meant to avoid. The two-core shape is the visible price of that choice, and it is paid deliberately, not incidentally.
